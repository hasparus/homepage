Adding a simple version history to any Y.js is way easier than you'd expect.

Sure, to build a nice one, we'd have to model for that. Do some event sourcing
or Redux shenanigans, model the actions.

But if we don't need all that, and just want to see how the doc changed, it's
enough to do this:

```ts twoslash file=../src/own/bear-fit/replayHistory.ts

```

The slider chooses a point in time i.e. how many saved updates to replay into a
separate `Y.Doc`.

I wanted this for a recurring meeting without a fixed time slot. I'd make a
calendar for two or three months, and people's availability would change along
the way. Having a history helped choosing the dates, because we could see how
fast are the dates disappearing and reappearing.

## Getting the updates

bear-fit already used y-partykit. With history persistence enabled, it keeps the
update log needed for replay:

```ts twoslash file=../src/code-blocks/y-travelling/persistence.ts

```

A copy of the current document won't give you those intermediate versions. Even
history mode can compact the log, merging earlier updates and losing the
versions between them. These examples use y-partykit 0.0.32.

The function for reading the log, `getLevelUpdates`, wasn't exported, so I
[copied it][server-source]. It calls the exported `getLevelBulkData` with this
key range:

```ts twoslash file=../src/code-blocks/y-travelling/getLevelUpdates.ts

```

Those keys are y-partykit's internal storage format. Not very nice of me, but we
have tests, and y-partykit is open source, so I can track any changes there.

## Fetching the history

I added `GET /parties/main/:room/history` to the server class containing
`onConnect`:

```ts twoslash file=../src/code-blocks/y-travelling/historyEndpoint.ts

```

The `clock` comes from an incrementing storage counter, not the time somebody
clicked a day. A record doesn't necessarily correspond to one click either. The
[encoder][encoder-source] writes each record as:

```text
clock length | update length | UTF-8 clock | Y.js update
   4 bytes   |    4 bytes    |            |
```

Both lengths are unsigned 32-bit integers, big-endian. Y.js updates can contain
newline bytes, so splitting the response on newlines isn't safe.

The decoder reads both lengths from the eight-byte header. It decodes the clock
as UTF-8 and copies the update bytes, then advances to the next record. If a
header or record is truncated, it throws instead of returning a partial result:

```ts twoslash file=../src/own/bear-fit/decodeHistoryUpdates.ts

```

The browser fetches the endpoint and decodes its response:

```ts twoslash file=../src/own/bear-fit/fetchHistory.ts

```

## Caching the previews

The demo rebuilds the document on every slider move. For a longer log, we can
instead replay it once and keep the last 250 versions as plain data:

```ts twoslash file=../src/code-blocks/y-travelling/cacheCalendarHistory.ts

```

Each snapshot copies the maps, so applying the next update doesn't change the
versions already saved. The slider can read `versions[index].snapshot` without
running any Y.js code. Rebuild the cache when the fetched history changes,
including after compaction.

I [benchmarked this][replay-benchmark] with 10,000 generated updates, in
Chromium with 4× CPU throttling on an M1 Pro. Rebuilding took about 17 ms per
backward step. The cache took 31 ms to build, and lookups after that were too
fast for the browser's clock. Node puts them at about 80 nanoseconds.

The 17 ms is thanks to the `doc.transact` in `replayHistory`. Without it, Y.js
finishes a transaction after every single update, and the same rebuild took 61
ms.

In Node, without the throttling, a rebuild is 5 ms and fits in a frame. At
50,000 updates it's 29 ms, and that's where I'd reach for the cache.

The cache is cheap here because the calendar is tiny. Four people, three weeks,
84 keys at most. Every version copies all of them, so you pay for how **wide**
the document is.

I widened the benchmark to 40 people over a year. Same 10,000 updates, 5,501
keys. In Node, building the cache went from 9 ms to 583 ms, and it held 56 MB.

For a document like that, store an encoded Y.js update every 32 versions and
replay the few updates past it. That took 29 ms to build and 3 MB to keep, and a
seek cost about 6 ms.

<aside>
  Applying an old update to the live document doesn't undo later changes.
  bear-fit restores a version by reading its application data and writing that
  data into the live document, as if it was a new change. The demo only previews
  versions.
</aside>
