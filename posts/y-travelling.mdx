Adding a simple version history to any Y.js is way easier than you'd expect.

Sure, to build a nice one, we'd have to model for that. Do some event sourcing
or Redux shenanigans, model the actions.

But if we don't need all that, and just want to see how the doc changed, it's
enough to do this:

```ts twoslash file=../src/own/bear-fit/replayHistory.ts

```

The slider chooses how many saved updates to replay into a separate `Y.Doc`.
In [bear-fit], I pass that document through the existing calendar's React
context and disable editing. Looking at an old version leaves the live one
alone.

I wanted this for a recurring meeting without a fixed time slot. I'd make a
calendar for two months, and people's availability would change along the way.
Sometimes it helped to look back before messaging the group.

Try marking a few days in the calendar above, then moving the slider back.

## Getting the updates

bear-fit already used y-partykit. With history persistence enabled, it keeps
the update log needed for replay:

```ts twoslash file=../src/code-blocks/y-travelling/persistence.ts

```

A copy of the current document won't give you those intermediate versions.
Even history mode can compact the log, merging earlier updates and losing the
versions between them. These examples use y-partykit 0.0.32.

The function for reading the log, `getLevelUpdates`, wasn't exported, so I
[copied it][server-source]. It calls the exported `getLevelBulkData` with this
key range:

```ts twoslash file=../src/code-blocks/y-travelling/getLevelUpdates.ts

```

Those keys are y-partykit's internal storage format. Check them before
upgrading.

## Fetching the history

I added `GET /parties/main/:room/history` to the server class containing
`onConnect`:

```ts twoslash file=../src/code-blocks/y-travelling/historyEndpoint.ts

```

The `clock` comes from an incrementing storage counter, not the time somebody
clicked a day. A record doesn't necessarily correspond to one click either.
The [encoder][encoder-source] writes each record as:

```text
clock length | update length | UTF-8 clock | Y.js update
   4 bytes   |    4 bytes    |            |
```

Both lengths are unsigned 32-bit integers, big-endian. Y.js updates can contain
newline bytes, so splitting the response on newlines isn't safe.

The decoder reads both lengths from the eight-byte header. It decodes the clock
as UTF-8 and copies the update bytes, then advances to the next record. If a
header or record is truncated, it throws instead of returning a partial result:

```ts twoslash file=../src/own/bear-fit/decodeHistoryUpdates.ts

```

The browser fetches the endpoint and decodes its response:

```ts twoslash file=../src/own/bear-fit/fetchHistory.ts

```

## Showing an old version

The slider's position supplies `count` to the replay function. Later updates
may depend on earlier ones, so limiting the slider to recent versions doesn't
mean you can discard the start of the log.

The [embedded calendar][demo-source] takes plain data, so I read the maps from
the replayed document before destroying it:

```ts twoslash file=../src/code-blocks/y-travelling/readHistoricalCalendar.ts

```

<aside>
  Applying an old update to the live document doesn't undo later changes.
  bear-fit restores a version by reading its application data and writing that
  data into the live document. The demo only previews versions.
</aside>

## Time-travel-ish

When I tweeted about this, [Jani Eväkallio][jani], who created [Foam], replied:

> Y.js history works well as long as the edits are synced roughly in order, but
> with multiple clients with long latencies or offline sessions, the history no
> longer represents linear time.
>
> Seems good for your use case, but I learned this the hard way, so just heads
> up!

Someone can edit offline and sync after everyone else. Replaying the stored
updates puts that edit later in the sequence, even though they made it earlier.

I asked whether this was a rich-text problem. He said the intermediate states
are easier to spot when text stops making sense, but Maps and Arrays can have
the same issue.
