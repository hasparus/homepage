Adding a simple version history to any Y.js is way easier than you'd expect.

Sure, to build a nice one, we'd have to model for that. Do some event sourcing
or Redux shenanigans, model the actions.

But if we don't need all that, and just want to see how the doc changed, it's
enough to do this:

<Twoslash code={replay} />

Make a fresh document and apply the first `count` saved updates. Stop where you
want to look. The live document hasn't changed.

I added this to [bear-fit]. I used to make two-month calendars for a recurring
meeting without a fixed time slot. People's availability changed, and sometimes
it helped to look back before messaging the group.

The app already used Y.js and y-partykit. I hadn't designed for history. I copied
one internal from y-partykit and added a slider.

Okay, but where do the updates come from?

## Keeping the past

You need to have kept them somewhere. In bear-fit, that's y-partykit's history
persistence mode:

<Twoslash code={persistence} />

I've left out the calendar setup and callbacks. This option tells y-partykit to
keep an update log. Without that log, a copy of the current document won't give
you all the intermediate versions back.

<aside>
  These examples use y-partykit 0.0.32. Its history mode can compact the log when
  it reaches its limits, replacing earlier updates with a merged state. You can
  replay what remains, but you lose the intermediate versions it compacted.
</aside>

## Borrowing an internal

There was a function called `getLevelUpdates` that did what I needed. It wasn't
exported. Probably for a reason.

I copied it anyway. With the optional arguments and key helper inlined, it looks
like this:

<Twoslash code={storage} />

`getLevelBulkData` *is* exported. We ask it for the document's update records,
using y-partykit's storage keys. The [full helper][server-source] keeps the
optional arguments and types.

This depends on an internal storage format. Check it before upgrading
y-partykit.

The fourth part of an update key is its `clock`, an incrementing storage
counter. It isn't a timestamp. A stored record doesn't necessarily correspond
to one click either.

## Fetching the history

I added a `GET /parties/main/:room/history` endpoint. This is the HTTP part of
the same server class as `onConnect`, with the other routes removed:

<Twoslash code={endpoint} />

The response contains clocks and binary Y.js updates. Each record starts with
two lengths:

```text
clock length | update length | UTF-8 clock | Y.js update
   4 bytes   |    4 bytes    |            |
```

Both lengths are unsigned 32-bit integers, big-endian. The [encoder][encoder-source]
writes the lengths, then copies the clock and update bytes after them.

<aside>
  The code I originally pasted into this post split the response on two newline
  bytes. A binary update can contain those bytes too. The current implementation
  uses lengths instead.
</aside>

This is the decoder used by the demo:

<Twoslash code={decoder} />

`DataView` reads the lengths. `TextDecoder` handles the clock. The update stays
a `Uint8Array`, ready for `Y.applyUpdate`.

## Rendering the past

In bear-fit, I pass the reconstructed `Y.Doc` through the same React context as
the live document. The calendar renders it with editing disabled. I didn't need
to build another calendar UI.

The blog demo uses Solid. It reads the reconstructed document into a plain
snapshot and destroys the temporary `Y.Doc`. Separated from the UI code, that
step looks like this:

<Twoslash code={snapshot} />

Those map names come from bear-fit's data model. This example combines the
[demo's][demo-source] document reader and cleanup into one function. The UI keeps
the snapshot and its clock together, so incoming edits don't move you to another
version while you're looking at the past.

For this post, I limited the slider to 250 past versions. It still replays the
earlier updates needed to construct them. Slicing the log down to its last 250
records *before* replay would lose that earlier state.

The history endpoint isn't a live feed. The demo fetches it after the document
changes and retries a few times if storage hasn't caught up yet.

I rebuild the document on every slider move. Moving forward could just apply
the next updates to an existing preview. I haven't needed that optimization.

<aside>
  Restoring is a separate operation. bear-fit reads the historical document as
  application data and writes it into the live document with
  `overwriteYDocWithJson`. Applying an old Y.js update to the live document
  doesn't undo later changes. The demo on this page only previews history.
</aside>

## Time-travel-ish

When I posted about this, [Jani Eväkallio][jani], who created [Foam] and
worked on the writing tool verb.ai, pointed out a catch:

> Y.js history works well as long as the edits are synced roughly in order, but
> with multiple clients with long latencies or offline sessions, the history no
> longer represents linear time.
>
> Seems good for your use case, but I learned this the hard way, so just heads
> up!

An edit can arrive long after someone made it. Replaying the stored updates
won't necessarily show what people saw at the time.

I asked whether this was a rich-text problem. He said the intermediate states
are easier to spot when text stops making sense, but Maps and Arrays can have
the same issue.

I wouldn't use this to settle an argument about who changed what first. It did
the job for my calendars.
